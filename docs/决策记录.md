## ADR-001 · 先设计、后编码

- **日期**：2026-11-10
- **状态**：已确认（用户明确要求）
- **背景**：产品涉及化学数据 + 交互规则 + 配方计算三块，边界不清就动手会导致大幅返工。
- **结论**：在用户确认 `docs/05-待拍板问题.md` 之前，不写页面代码。
- **理由**：数据模型与交互规则决定 80% 的代码结构；先定规则可避免反复重构。

## ADR-002 · 存档机制：快照目录 + CHANGELOG

- **日期**：2026-11-10
- **状态**：已确认（用户要求"每次大修改前都要存档"）
- **选项**：
  - A 只靠 git 分支/提交
  - B 每次复制整个项目到 `archive/<时间戳>-<标签>/`
  - C 两者都做
- **结论**：**B 为主**（`scripts/snapshot.ps1`），每次快照内含 `MANIFEST.md`（文件清单 + SHA256 + git 提交号）。
- **理由**：快照目录对非程序员友好、可肉眼回滚；git 作为可选补充。存档只复制不删除。

## ADR-003 · 数据以静态 JSON 内置前端

- **日期**：2026-11-10
- **状态**：已确认（Q4 = 纯本地，无后端）
- **选项**：静态 JSON 内置 · 外部 API · 后端数据库
- **倾向**：静态 JSON。首版数据量（60 食材/120 分子）压缩后 < 300 KB，完全可以内置；离线可用、零运维、加载快。
- **代价**：数据更新要靠重新构建/重新导入 JSON。

## ADR-004 · 规则引擎用"角色通配"而非穷举食材对

- **日期**：2026-11-10
- **状态**：已确认（Q2 = 60 食材，穷举不可行）
- **背景**：60 食材两两组合 = 1770 对，手写不可维护。
- **结论**：交互规则以 `role:*`（如 `role:acid-juice × role:dairy`）+ 分子族匹配为主，少量精修规则覆盖通配规则。
- **理由**：可扩展到 200+ 食材而不线性增加工作量；且天然带"通用解释"，便于教学。

## ADR-005 · 交互不判定"好/坏"，判定"效应 + 是否合意"

- **日期**：2026-11-10
- **状态**：已确认（Q2/Q8 定稿后不再变动）
- **背景**：奶洗是"沉淀"（看起来是冲突），但它是被追求的效果；乌佐浑浊同理。
- **结论**：数据层记录 `effect`（协同/掩蔽/沉淀/变色/乳化…）+ `verdict`（推荐/注意/避免），
  UI 用"效应"着色，并允许用户切换"我想要/我不想要这个效果"。
- **理由**：避免把正确答案判成错误（这是同类产品最常见的失败点）。

## ADR-006 · 「分子操作台」的定位：第二个核心界面，不是小工具

- **日期**：2026-11-10
- **状态**：已确认（用户提出；具体形态由我定义，待用户复核）
- **定义**：拖拽分子 → 拨动条件（pH/温度/时间/乙醇/氧气/光照）→ 看见可行反应与产物 → 反查现实做法。
- **理由**：列表式界面只能回答"是什么"，回答不了"放在一起会怎样"；而后者才是调酒时真正的思考动作。
- **边界**：明确不是分子动力学模拟器，只做规则 + 查表 + 示意动画（见 `06-分子操作台.md` §9）。

## ADR-009 · 无酒精模式作为独立维度，而非附属标签

- **日期**：2026-11-10
- **状态**：已确认（X2 = 做）
- **结论**：全局 ABV=0 模式；额外增加一条硬规则——无乙醇时疏水香气承载能力差，需乳化/增稠/油脂。
- **理由**：无酒精不是"去掉酒"，而是换了溶剂体系，物理化学完全不同，把它当标签会误导用户。

## ADR-011 · 顶层导航按「任务」分区，不按「数据类型」分区

- **日期**：2026-11-10
- **状态**：已确认（用户指示："分成几个不同的功能…根据现有食材推荐一个，自己试验一个"）
- **背景**：v0.1 的导航是食材库/分子库/搭配实验室/技法库——按内容分类，用户打开后仍不知该点哪里。
- **选项**：
  - A 保留内容分类 + 加一个首页
  - B 改为按任务分区的四个模式（推荐 / 试验 / 分子 / 资料）
- **结论**：**B**。前三个是功能（各自完成一件事），第四个是资料底座。
- **理由**：用户的真实状态是"我有材料想喝点什么"或"我想自己调"，不是"我要查一个分子"。
  按任务分区才能让零基础用户 30 秒内得到结果。
- **代价**：数据层（食材/分子）不能作为顶层入口，必须通过全局搜索与内链被发现。
  这要求所有提到食材/分子/技法的名字都可点击，否则资料库会被埋没。

## ADR-012 · 三模式共用同一个 Engine，不做三套逻辑

- **日期**：2026-11-10
- **状态**：已确认
- **结论**：`DataStore / RoleMatcher / InteractionSolver / ReactionSolver / Calc / Explainer / Store`
  七个子模块，被四个模式共同调用。
- **理由**：若推荐台与试验台各写一套计算，同一杯酒在不同页面会给出不同 ABV，直接摧毁可信度。
  这是必须在第一行代码之前定下来的架构约束。

## ADR-013 · 技法（Technique）升为一等对象，工作台成为产品中心

- **日期**：2026-11-10
- **状态**：已确认（用户指示："不止要经典调酒的，我主要需要的是类似低温慢煮等分子鸡尾酒技法的化学风味工作台"，m00298）
- **背景**：v0.3 的四模式里，"试验台"本质是配比计算器（拉毫升数看 ABV/糖/酸），
  能做出好喝的 Highball，但做不出"低温慢煮草莓伏特加""奶洗澄清菠萝汁""反向球化苦精珠"。
  真正区分分子鸡尾酒的是**技法**，其变量是温度 × 时间 × 压力 × pH × 剪切，而不是比例。
- **选项**：
  - A 在现有试验台里加一个"技法"选项（补丁式）
  - B 新建独立的技法台，导航变五区 `推荐 · 技法 · 配方 · 分子 · 资料`，原试验台改名配方台
- **结论**：**B**。对象顺序倒过来：`技法 → 备料 → 配方 → 一杯酒`。
  经典骨架（Sour / Highball 等）降级为下游用法，不再占据中心。
- **理由**：技法参数比配方骨架**稳定**（低温慢煮 65℃/90min 十年不变，爆款配方每季都换），
  先做技法台能让数据基础更持久；且技法台是差异化本身，配色/交互都为它设计才值。
- **代价**：导航从四项变五项，移动端需要底部五格；"备料（Prep）"要成为新的数据实体，
  配方台的配料行必须能引用备料，这是额外的一层间接。

## ADR-014 · 用同一个 ConditionVector 描述技法参数、分子台拨盘与配方工艺

- **日期**：2026-11-10
- **状态**：已确认
- **结论**：定义 `ConditionVector{ tempC, timeMin, pressure, ph, ethanolPct, shear, oxygen, light, enzyme, ions }`，
  技法 = 命名好的 ConditionVector + 操作序列 + 设备 + 预期产物；分子台是手动拨这个向量；试验台是食材 × 这个向量。
  `ReactionSolver` 只接受 ConditionVector，不再接受散装参数。
- **理由**：否则会出现"分子台说 65℃ 不触发美拉德、技法台说触发"的自相矛盾，
  同一个错误会以两种面目出现在两页，用户一旦发现就再也不信这个产品。这是 ADR-012 的直接延伸。
- **代价**：早期就要把参数模型抽象对，技法的特殊参数（料液比、剂量、酶种）要以 `Partial<ConditionVector>` 扩展字段承载，
  不能在 Technique 里另起一套平行结构。
## ADR-015 · 技法台以「材料 → 目标 → 推荐」为入口，技法目录降为词典

- **日期**：2026-11-10
- **状态**：已确认（用户 m00417 直接修正）
- **结论**：技法台首屏不是 20 条技法清单，而是三段式：① 选材料 → ② 选目标（更香/更清澈/更有口感/更好看/更省事）
  → ③ 推荐 3 条技法（每条含适配度、化学理由、材料角色、参数摘要、产物、风险）。选中后进入参数工作台。
  20 条技法目录只在资料库与"全部 20 条"入口出现。不可用技法必须列出并说明原因。
- **理由**：用户在不知道技法能做什么之前，没有能力从 20 个陌生名词里做选择；
  让用户先表达"我有什么 + 我想要什么"，系统再回答"那你能用什么"，决策成本从 20 选 1 降到 3 选 1。
  "不适用也显示原因"是产品可信度的来源：它证明系统真的在算，而不是在随机推荐。
- **代价**：`TechniqueSolver.filter()` 必须可靠，材料 role 标注与条件冲突检查成为数据质量的瓶颈；
  推荐错了比不推荐更伤。首版宁可比对少（3 张卡）也不能给错。
## ADR-016 · 前中后调按「挥发时间层」定义，香型（Facet）作为独立对象

- **日期**：2026-11-10
- **状态**：已确认（用户 m00485 提出需求）
- **结论**：技法台增设第二入口「我只有一样材料 → 先定香调」。
  前调 / 中调 / 后调 **不按香气类别划分，而按挥发时间划分**（0–5 min / 5–30 min / 30 min+），
  判据是沸点、logP、阈值三个可测量。中间引入 `Facet`（香型）对象：材料 → 关键分子 → 香型 → 用户选香型。
  `Facet` 由分子属性自动聚类、人工校对，不手工维护。
- **理由**：调酒书里的"前中后调"是通感修辞，无法计算，也就无法推荐。
  改成时间层之后，它可以被算出来、被可视化、还能与技法参数联动（65℃/90min 会毁掉青绿香，所以选技术法前就该知道）。
  引入 Facet 是因为用户认得"青草味"但不认得"(Z)-3-己烯醛"；分子只用于解释与冲突检测。
- **代价**：需要为 120 个分子补沸点 / logP / 阈值 / 时间层字段，这是数据量最大的一块；
  「香型存活率」初版只能按温度衰减粗估，必须标"估算"，否则会变成假精度。
## ADR-017 · 香型用「颜色 + 图形」双编码；每层可换一换；专业模式默认关

- **日期**：2026-11-10
- **状态**：已确认（用户 m00542 答复：①专业模式开关保留 ②时间边界不变 ③每层加换一换 ④存活率保留 ⑤香型要颜色/符号）
- **结论**：
  1. 每个香型固定一组 **颜色 + 图形** 双编码：熟果甜香 `●` `#B4693A`、青绿鲜草 `▲` `#4F7A46`、
     花香 `❀` `#8A6E92`、焦糖奶油 `◆` `#7B5230`、酸鲜 `✦` `#B9A03C`。
     材料卡、存活率条、时间轴、构成清单全部复用同一符号。
  2. 前 / 中 / 后每列头部带 **「换一换 ↻」**，一次换掉该层 4 个候选中未选的若干条。
  3. **专业模式**为全局开关，默认关闭。关闭时只显示香型名与机制说明；开启后显示分子名、阈值、logP、CAS。
- **理由**：
  1. 只靠文字，5 个香型在扫视时没有形状差异，切换会变慢；只用颜色又对色觉障碍不友好，
     所以形状必须承担信息，颜色只做加速。这套符号要成为全站词汇表的一部分，不是装饰。
  2. 三层各 4 条候选一定覆盖不全（用户的冰箱比我们的数据库更杂），换一换是"我的情况比较怪"的出口。
  3. 分子名对专业用户是可信度证据，对家庭用户是噪音。开关让两类人共用一套界面而不互相牺牲。
- **代价**：符号表一旦确定就要在 04 / 05 / 资料库 / 配方卡四处统一，改一次全站改；
  换一换需要候选池大于 4 条（每层至少 10 条起），数据量比"每层 4 条"翻一倍以上。

## ADR-018 · 食材拆成两张表：植物性食材 / 基底液体

- **日期**：2026-11-10
- **状态**：已确认（用户 m00759：「食材表只要水果蔬菜香料干果之类的，基酒，气泡之类的单开一张，只在选材料的时候加入，
  意思就是我要的是列出我有的蔬果香料之类的食材来推荐组合还有做法」）
- **结论**：
  1. **表 A · 植物性食材**（`data/ingredients.json`）：水果 / 蔬菜 / 香草 / 香料 / 干果 / 花与茶。
     每条含 ≥3 个可解释关键分子、酸度、糖、质地、可用的技法、搭配与风险。
  2. **表 B · 基底液体**（`data/bases.json`）：烈酒 / 发酵酒 / 无酒精基底 / 气泡 / 乳与甜味剂。
     字段只保留对配比计算有用的：ABV、糖、酸、气泡、密度、用法角色（基酒/调和/延长/点缀）。
  3. 两张表**在选材料这一步汇合**：先勾"我有什么蔬果香料"，再勾"我有什么酒和气泡"。
     推荐引擎里的 `cover` 只统计表 A，`structure` 只统计表 B。
- **理由**：
  1. 用户真正的痛点不是"没有酒"，是**冰箱里那几样东西怎么变成一杯**。把基酒和蔬果混在一张 60 条的表里，
     会让"我有什么"这个问题一半答案是"我买不起的基酒"，推荐结果立刻失真。
  2. 两张表的数据性质不同：蔬果要的是**分子与风味**，基底要的是**ABV/糖/酸/气泡**这类可加总的数值。
     混表会让字段一半永远空着。
  3. "只在选材料的时候加入"也解释了为什么基底表可以小：用户家里通常 3–6 支酒，选择动作是一次性的；
     蔬果香料才是每次变化的变量。
- **代价**：推荐引擎要处理两段式选材（先 A 后 B），否则会出现"有配方没酒"；
  表 A 的分子标注工作量大（60 条 × 3 个分子 = 180 个引用），且要能对上已有的 143 条分子表。
