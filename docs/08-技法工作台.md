# 08 · 技法工作台（化学风味工作台）

> 用户 clar：`不止要经典调酒的，我主要需要的是类似低温慢煮等分子鸡尾酒技法的化学风味工作台`（m00298）
>
> 一句话：**这个产品的中心不是"调一杯经典鸡尾酒"，而是"对食材施加一个物理化学条件，看它怎么变，再把变出来的东西调进酒里"。**
> 经典配方（Sour / Highball 骨架）降级为"下游用法"，技法才是上游。

---

## 1. 为什么会走到这一步（诊断）

v0.3 的四模式（推荐 / 试验 / 分子 / 资料）里，"试验台"实际是个**配比计算器**：选食材、拉毫升数、看 ABV/糖/酸。
这能做出一杯好喝的 Highball，但做不出"低温慢煮草莓伏特加""奶洗澄清的菠萝汁""反向球化的苦精珠"。

真正把分子鸡尾酒和普通调酒区分开的，是**技法（technique）**：

| 普通调酒 | 分子/现代技法 |
|---|---|
| 摇、搅、兑、捣 | 低温慢煮、油洗、奶洗、澄清、球化、凝胶、泡沫、旋转蒸发、离心、冷冻浓缩、快速陈化 |
| 变量是"比例" | 变量是"温度 × 时间 × 压力 × pH × 剪切" |
| 结果是一杯酒 | 结果是**一个半成品（prep）**，再被组合进一杯酒 |

所以工作台的对象顺序要倒过来：**技法 → 产物（备料）→ 配方 → 一杯酒**。

---

## 2. 关键统一：一个 ConditionVector 贯穿全站

四个界面以前各算各的。现在统一到一个**条件向量**上——它既是技法参数，也是分子台拨盘的位置，还是试验台的工艺：

```ts
type ConditionVector = {
  tempC: number;        // −20 … 250
  timeMin: number;      // 0.2 … 43200（30 天）
  pressure: 'vacuum' | 'atm' | 'pressurized';
  pressureBar?: number; // 真空 −0.9，加压 0–6
  ph: number;           // 1 … 9
  ethanolPct: number;   // 0 … 70
  shear: 0 | 1 | 2 | 3; // 静置 / 搅 / 均质 / 离心（g 值另存）
  oxygen: 'none' | 'low' | 'air' | 'pure';
  light: 'dark' | 'ambient' | 'uv';
  enzyme?: 'pectinase' | 'amylase' | 'protease' | 'lactase' | 'glucoamylase';
  ions?: { ca2?: number; fe3?: number; mg2?: number }; // mmol/L
};
```

**技法 = 一个命名好的 ConditionVector + 一条操作序列 + 一台设备 + 一组预期产物。**
分子台 = 手动拨这个向量，看单个反应。
试验台 = 食材 + 这个向量 → 成品读数。
推荐台 = 反推：想要某种风味 → 该用什么技法。

> 这样做的直接好处：**同一套 `ReactionSolver` 同时驱动分子台和技法台**，不会出现"分子台说 65℃ 不会美拉德、技法台说会"的自相矛盾。这是 ADR-012（共享 Engine）的延伸。

## 3. 信息架构：五区

```
推荐 · 技法 · 配方 · 分子 · 资料
 ↑      ↑      ↑      ↑      ↑
 反推   工作台  组装   原理   数据库
```

| 区 | 回答的问题 | 主对象 |
|---|---|---|
| **推荐** | 我手上有这些，能做什么？ | 方案卡（3–5 张） |
| **技法** | 我对这块食材做这个操作，会发生什么？ | 技法 × 食材 → 备料 |
| **配方** | 把这些备料和食材按比例拼成一杯。 | 一杯酒（原试验台） |
| **分子** | 底层到底在发生什么反应？ | 反应（R1–R12 扩展） |
| **资料** | 这个食材/分子/技法是什么？ | 词条 |

原来的"试验台"改名为 **配方台**，因为它的粒度是"一杯"；新的**技法台**粒度是"一批备料"。
两者通过 `备料 → 送进配方台` 连接。

**首版顺序（改）**：技法台 → 资料库 → 配方台 → 推荐台 → 分子台。
理由：技法台是差异化所在，也最先需要数据（技法参数比配方骨架稳定得多）。

### 3.1 技法台的入口（v0.7 修正）

> 用户原话（m00417）：「我需要的是选择材料之后再推荐并选择技法，而不是把所有技法列出来」

v0.6 把 20 条技法做成左侧目录直接铺开，等于让用户在 20 个陌生名词里自己找。错的不是技法清单，是**顺序**：先有材料和意图，技法才有意义。

新入口是三段式，一条主线，不许跳步：

```
① 选材料  →  ② 选目标  →  ③ 推荐 3 条技法  →  选中 → 进参数工作台（v0.6 那张）
```

**① 选材料**：芯片式，可加可删，也能直接打字（"还有半颗青柠和一点迷迭香"会走 NLP 解析）。

**② 选目标**：`更香 / 更清澈 / 更有口感 / 更好看 / 更省事`。
同一个材料组合，换目标就换排序——**同一批材料没有唯一正确答案**，这一句要写在界面上。

**③ 推荐**：只给 3 张卡，每张必须回答四件事：

| 字段 | 回答的问题 | 为什么必须有 |
|---|---|---|
| 适配度 % | 这条技法有多适合这批材料 | 可比较，避免"都对" |
| 为什么是它 | 化学层面的理由 | 无解释不展示（沿用推荐台原则） |
| 材料角色 | 每个材料在这条技法里扮演什么 | 用户才知道"原来伏特加是溶剂" |
| 参数摘要 + 产物 + 风险 | 大致会得到什么、会在哪失败 | 决策成本最低的三个数 |

**筛选算法四步**（`TechniqueSolver.filter()`）：

1. **角色匹配**：材料打 role 标签（溶剂 / 被萃取物 / 结构剂 / 酸源 / 糖源 / 乳蛋白 / 酶底物…），技法声明所需角色，取交集。
2. **条件冲突检查**：算这批材料混合后的 pH、乙醇、糖度，与技法参数的安全区求交。**不交则不可用**。
3. **设备可用性**：用户在设置里勾了哪些设备（慢煮机 / 虹吸瓶 / 离心机 / 真空泵 / 液氮…）。没有就直接排除，只保留原理说明。
4. **目标加权**：按 ①香气保留 ②澄清度 ③结构 / 口感 ④颜值 ⑤步骤数 五个维度打分排序。

**不可用技法也必须显示，但要给原因**——这是本产品与"推荐算法"最大的区别：

> 奶洗 T8 —— 缺乳蛋白：奶洗靠酪蛋白在 pH 4.6 絮凝，这批材料里没有乳制品。
> 球化 T13 —— pH 太低：柠檬汁把体系拉到 3.1，海藻酸钠在 pH < 3.5 不成胶。
> 旋转蒸发 T5 —— 缺设备：需要 100–200 mbar 真空泵，设置里没勾。

用户看完"为什么不行"，比看三条"为什么行"学到的更多。**不适用 ≠ 不显示。**

**20 条技法目录降级**：不再作为默认入口，只在两处出现——资料库的"技法"栏，以及技法台右下角的"全部 20 条技法 →"。它是词典，不是菜单。

**材料判读面板**：右栏常显，四行写清每样材料被系统读成了什么（软果 / 中性烈酒 / 酸源 / 糖源），以及关键数值（pH 2.2、40% ABV、果胶高）。这是"为什么只有这三条"的透明化，也让用户学会自己判断。

## 4. 技法目录（首版 20 个）

分四族。每个技法的字段固定：`参数范围 / 化学机制 / 产物 / 失败模式`。

### A. 萃取族 Extraction

| # | 技法 | 关键参数 | 化学机制 | 产物 | 失败模式 |
|---|---|---|---|---|---|
| T1 | **低温慢煮 Sous-vide** | 40–85℃ / 30min–4h / 真空 −0.9 bar | 细胞壁果胶水解（β-消除）、色素与糖溶出；低温让酯类/萜烯挥发损失最小 | 风味基酒、果泥糖浆 | >75℃ 香气陡降、出"果酱味"；袋漏气→氧化褐变 |

| T3 | **快速浸渍 Rapid infusion** | N₂O 1–3 次加压 / 30s–3min | 压力驱动细胞破裂，溶剂快速进入细胞 | 即用浸渍酒 | 时间过长→苦涩；泄压太快→喷溅 |
| T4 | **冷萃 Cold brew** | 4–20℃ / 8–24h | 低温只溶出小分子香气与糖，单宁/咖啡因溶出少 | 冷萃茶酒、冷萃咖啡 | 温度高→涩；时间短→空 |
| T5 | **旋转蒸发 Rotovap** | 40–60℃ / 100–200 mbar | 减压使沸点降低，热敏香气在低温下蒸出 | 香气馏分、脱醇酒 | 真空度不够→煮熟味；冷凝不足→损失 |
| T6 | **冷冻浓缩 Freeze concentration** | −18℃ / 6–24h | 水先结冰，把溶质挤到未冻液相 | 2–4× 浓缩液 | 冻太慢→冰晶夹带；反复冻融→氧化 |
| T7 | **脱水 / 风味粉** | 40–70℃ 热风 / 冻干 / 麦芽糊精 20–50% | 水分活度下降抑制降解；糊精包埋挥发性物质 | 风味粉、脆片 | 温度高→美拉德过头、焦味 |

## 5. 工作台界面：四层结构

一屏四层，从上到下就是"你想干什么 → 你调什么 → 发生了什么 → 得到什么"：

```
┌──────────────────────────────────────────────────────────────┐
│ ① 技法库（左栏 250px）                                        │
│    萃取 / 澄清 / 结构 / 熟成 四族，20 条                     │
│    每条：编号 · 名称 · 一句参数摘要                           │
├───────────────────────────────┬──────────────────────────────┤
│ ② 参数区                       │ ④ 产物面板（右栏 380px）     │
│    温度 / 时间 / 压力 / 料液比  │    产物名 + 产量             │
│    （每项带"推荐区间"与"危险区"）│    香气强度 / 色深 / 澄清度  │
│                                │    成分变化（酯 +38%…）      │
│ ③ 化学过程区（中栏）            │    失败模式 3 条             │
│    时间轴泳道：细胞破裂→溶出→   │    设备清单                  │
│    水解→萃取完成→氧化衰退       │    [送进配方台] [存为备料]   │
│    三条实时状态条               │                              │
└───────────────────────────────┴──────────────────────────────┘
```

### 界面上的四条硬规则

1. **参数必须有"推荐区间"和"危险区"两段色带**，不是裸滑块。用户拉出区间时立刻看到"会发生什么"，而不是拉完才报错。
2. **时间轴按真实时间比例画**（对数轴），90 分钟和 90 秒在视觉上不能一样长——这正是"预调瓶放三天更好喝"能被理解的地方。
3. **产物面板永远标"估算"**，并给置信度（文献 / 机理 / 共识 / 待验）。
4. **产物可以继续参与下一个技法**（慢煮 → 澄清 → 球化），形成"备料链"，链上每一步都可回看参数。这是分子料理真正的玩法。

## 6. 数据模型

```ts
type TechniqueFamily = 'extraction' | 'clarification' | 'structure' | 'aging';

type ParamSpec = {
  key: keyof ConditionVector | 'ratio' | 'dose';
  label: string; unit: string;
  min: number; max: number; step: number; default: number;
  scale?: 'linear' | 'log';
  safe: [number, number];      // 推荐区间
  danger?: [number, number][]; // 危险区（可多段）
  note?: string;
};

type TechniquePhase = {
  fromMin: number; toMin: number;
  name: string;                 // 细胞壁破裂 / 果胶水解 …
  chemistry: string;            // 机制一句话
  compounds?: string[];         // 涉及的 compound id 或 role:*
  visual: string;               // 色深/浑浊/质地
};

type Technique = {
  id: string;                   // 'sous-vide'
  no: number;                   // 1..20
  name: string; nameEn: string;
  family: TechniqueFamily;
  oneLiner: string;             // 一句原理
  params: ParamSpec[];
  phases: TechniquePhase[];
  outputs: { kind: string; yieldNote: string; dosage: string }[];
  equipment: string[];
  failureModes: { cause: string; symptom: string; fix: string }[];
  reactions: string[];          // 关联 R1..R12
  evidence: 'literature' | 'mechanism' | 'consensus' | 'unverified';
  sources?: string[];
};

type Prep = {                   // 备料：技法作用在食材上的结果
  id: string;
  techniqueId: string;
  inputs: { ingredientId: string; amount: number; unit: string }[];
  params: Partial<ConditionVector> & { ratio?: number; dose?: number };
  outputs: { name: string; volumeMl: number; intensity: number; clarity?: number }[];
  createdAt: number;
  notes?: string;
};
```

`Prep` 是新的一等公民：**配方台的配料行里可以出现"备料"，就像出现"青柠汁"一样**。

## 7. 引擎扩展（在 ADR-012 的七子模块上加两个）

| 模块 | 新增职责 |
|---|---|
| `TechniqueSolver`（新） | `(technique, inputs, params) → { phases, states, outputs, risks, advice }` |
| `PrepStore`（新） | 备料的持久化、备料链追溯、送进配方台 |
| `ReactionSolver`（改） | 接受完整的 `ConditionVector`，不再只吃 pH/temp/time 三个参数 |
| `Calc`（改） | 增加"按技法参数推产量/浓度"的估算函数 |

估算策略沿用 06 文档的诚实做法：**分级 + 区间 + 永带"估算"标签**，不伪造两位小数的科学感。

## 8. 与"资料库"的关系

技法本身是资料库的第四栏（食材 · 分子 · 反应 · **技法**）。
工作台里的每一个参数名、每一个化合物、每一个失败症状，都可点进词条——这是"可解释"原则的落地方式。
